# L2 行情持久层：数据存储与回源优化

## 一、问题

原架构把**历史不可变数据当成临时缓存**用，导致缓存一失效就重复拉取永远不会变的数据：

| 接口 | 冷启动回源次数 | 说明 |
|---|---|---|
| `/api/charts/limit-counts?days=60` | **≈120** | 按天循环打涨停池 + 跌停池，而 60 天前的涨停家数永不变 |
| `/api/overview` | **≈76** | 8×index_daily + 3×trade_cal + 2×daily + 31×index_member + 31×sw_daily |
| `/api/sectors` | **≈35** | 行业目录 + 逐行业取 K 线 + 成分股 |
| `/api/watchlist` | **N** | 每只自选股 1 次 sparkline |
| `/api/charts/futures-basis` | **≈5** | 现货指数 + 期货映射 + 逐合约日线 |

叠加三个结构性问题：

1. 缓存是**进程内内存** `TTLCache(maxsize=64)` —— 进程重启、LRU 淘汰、多 worker 全部清零重来
2. 缓存键只有 `time.time() + TTL`，**没有交易日维度**，无法表达"历史数据已定格，永不回源"
3. 数据库只存 `daily_snapshot` 一个 JSON blob，时序数据全部不落盘

## 二、核心原则

**按「数据可变性」分层，而不是按 TTL 分层。**

```
不可变历史 (trade_date < 最新交易日)  →  永久存储，命中即返回
当日已收盘 (已过 15:05 且已入库)      →  永久存储，只读
当日盘中                              →  内存短 TTL（60s）
```

读取路径：`L1 内存 TTL` → `L2 SQLite（按 trade_date 命中）` → `L3 数据源 API`

- **已定格**的数据：先读本地，命中即返回，零回源
- **盘中**数据：先取实时源，本地库仅作兜底
- 回填完成后主动清空 L1，避免继续吐回填前的旧数据

## 三、表结构（`api/app/models/market_data.py`）

| 表 | 主键 | 内容 | 年增行量 |
|---|---|---|---|
| `trade_calendar` | `trade_date` | 交易日历（按年同步，同步过就跳过） | 365 |
| `stock_daily` | `ts_code + trade_date` | 全市场个股日线（close / pct_chg / amount） | ~135 万 |
| `market_daily_agg` | `trade_date` | 预聚合：7 档分布 / 涨跌停数 / 成交额 / 涨停 TOP5 | 250 |
| `index_daily` | `ts_code + trade_date` | 指数日线（含 code / name） | ~2000 |
| `sector_daily` | `sector_code + trade_date` | 行业日线 + 领涨股 | ~9000 |
| `futures_daily` | `contract + trade_date` | IF / IH / IM 主力连续 | ~750 |
| `intraday_bar` | `code + trade_date + time` | 分时分钟线（收盘后固化） | ~48 万 |
| `stock_name` | `ts_code` | 代码 → 名称（涨停 TOP5 展示用） | ~5400 |
| `fetch_log` | `domain + ref_key` | **回源去重闸门** | 小 |
| `series_cache` | `cache_key` | 难建模数据的通用兜底 | 小 |

**明细 + 聚合双写**：`stock_daily` 保留原始行（可回溯重算任意指标），
`market_daily_agg` 存预聚合结果（查询 O(1)，不必每次扫 60×5400 行）。

存储成本：全市场日线约 70MB/年，SQLite 无压力。

## 四、去重机制：`fetch_log`

`(domain, ref_key)` 唯一。任何回源动作落库后**必须**登记，回填前先查差集：

```python
missing = await store.missing_ref_keys(session, DOMAIN_STOCK_DAILY_RAW, ["2026-08-26", ...])
```

ref_key 约定：

| 域 | ref_key |
|---|---|
| 日级全域（breadth / indices / sectors） | `2026-08-28` |
| 期货主力连续 | `2026-08-28:60d`（含当天，跨日自动重拉） |
| 分时固化 | `2026-08-28` |
| 交易日历 | `2026`（按年） |
| 股票名称 | `2026-08-28` |

## 五、回填服务（`api/app/services/backfill.py`）

**区间优先，日级兜底**：

- 指数 / 板块 / 期货 → 按区间一次拉（8~36 次请求覆盖一年）
- 个股日线 → 按日串行拉（Tushare `daily(trade_date)` 单次即返回全市场某一天，250 天 = 250 次请求）

限流：日间 0.25s / 域间 0.5s。单日或单域失败只记日志，下次运行自动重试。

### 触发方式

| 方式 | 说明 |
|---|---|
| 定时任务 | 每工作日 18:00（上海时区），回填近 5 个交易日后落收盘快照。不设在 15:35：数据源要到收盘后数小时才更新当日数据，过早回填会被 `fetch_log` 标记成已抓取，之后不再补 |
| 手动接口 | `POST /api/history/backfill?days=250`（需 API Token） |
| 启动自动 | `BACKFILL_ON_STARTUP_DAYS=250`，后台跑不阻塞启动；首次部署后改回 0 |

## 六、Provider 新增回填域

`provider.py` 能力矩阵新增 5 个域（前端不直接消费，仅供 L2 回填）：

| 域 | 主源 | 方法 |
|---|---|---|
| `stock_daily_raw` | tushare | `fetch_stock_daily_raw(trade_date)` |
| `index_range` | tushare | `fetch_index_range(start, end)` |
| `sector_range` | ths → tushare | `fetch_sector_range(start, end)` |
| `stock_names` | tushare | `fetch_stock_names()` |
| `calendar` | tushare | `fetch_trade_calendar(start, end)` |

降级链设计要点：**THS 快照类接口只能取当日，历史区间只有 Tushare 能补**。
`sector_range` 主源设 THS（当日质量好），历史区间自动降级到 Tushare。

## 七、收益

| 场景 | 改造前 | 改造后 |
|---|---|---|
| `limit-counts?days=60` 冷启动 | 120 次 | **0 次** |
| `overview` 冷启动 | 76 次 | 历史 0 次 / 当日 1~3 次 |
| `sectors` 冷启动 | 35 次 | **0 次** |
| `watchlist` sparkline × N | N 次 | **0 次** |
| `futures-basis` | 5 次 | **0 次** |
| 进程重启 | 全量重拉 | **0 次** |

首次上线一次性成本：约 250（日线）+ 8（指数）+ 32（板块）+ 3（期货）≈ **293 次请求**，
之后每个交易日仅 1~4 次（当日日线 + 增量补齐）。

## 九、已知限制

- **历史板块领涨股为 `—`**：领涨股需要「行业成分股 × 逐日全市场涨跌幅」比对，
  历史区间还原成本过高。仅区间最后一日补齐。如需要历史领涨股，
  后续可加 `sector_member` 表（约 5000 行，一次性 31 次请求）后用本地 `stock_daily` 计算。
- **`daily_snapshot` 仍是 JSON blob**：历史快照保持原样未改，与 L2 并存。
  后续可让快照改为从 L2 按日期重建，进一步省存储。
- 回填数据源依赖 Tushare（THS 无法补历史区间）。Tushare token 失效时历史回填会静默跳过，
  线上读取仍会实时降级到 THS，不影响可用性。
